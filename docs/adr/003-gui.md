# ADR-003 — Tauri 2 + Svelte, with pdf.js for preview

**Status:** Proposed
**Closes:** SRS §19 open decisions *"GUI framework"* and *"PDF preview implementation"*

## Context

SRS §11.1 sets two constraints and leaves the rest open: the UI *"should be implemented in or tightly controlled by the Rust application"* and *"should not require a browser-based server process."* §19 asks for a choice based on *"cross-platform maturity, text controls, accessibility, packaging, and PDF-preview integration."*

Four requirements do most of the deciding, and three of them are easy to underrate:

- **GUI-003 / GUI-004** — settings and style editing without TOML. Ordinary form controls; no framework struggles here.
- **NFR-011** — keyboard navigable, accessibility semantics supported by the toolkit.
- **NFR-012** — localizable GUI strings, English first.
- **GUI-008 / GUI-009** — an integrated PDF preview, with an explicit fallback if a platform cannot manage one.

And one requirement that is not in the GUI section at all but decides the question: the target user is *"a Bible publisher, translator, typesetter, ministry worker"* (§5.1) working in scripts including Tamil, Devanagari, Arabic, and Hebrew. **They will type those scripts into the settings UI** — a project name, a book name override, a font family. That means input-method composition, bidirectional text, and complex-script shaping in ordinary text fields.

## Options

### A — An immediate-mode Rust toolkit (rejected)

Pure Rust, one renderer on every platform, no web stack, small binaries. Genuinely attractive for a tool like this.

It loses on the three underrated requirements together. Input-method composition and complex-script editing in text fields are a known weak point of immediate-mode toolkits and are a *correctness* requirement for these users, not a polish item. Accessibility must be bolted on and is not equivalent to a native tree. And there is no PDF-preview story short of rasterizing pages through a separate crate and blitting them, which is GUI-008 rebuilt from parts.

Choosing A would mean owning text input, accessibility, and a PDF renderer as three project-sized problems that are not Bible composition.

### B — Native bindings per platform (rejected)

Best possible text and accessibility. Three UIs to build and maintain, for a two-panel-plus-log application. Not proportionate.

### C — Tauri 2 + Svelte (chosen)

## Decision

**Tauri 2 with a Svelte + Vite + TypeScript frontend, and pdf.js for the preview.**

**§11.1's constraint is satisfied, and the wording invites a misreading worth clearing up.** Tauri runs no local HTTP server and ships no Node runtime; the frontend is static assets served from inside the binary over a custom protocol, into the platform's own webview. The Rust application owns the process, the filesystem, the dialogs, and every privileged operation. "No browser-based server process" excludes an Electron-style local server; it does not exclude a webview.

**The webview supplies the three hard things.** Input methods, bidirectional text, and complex-script shaping come from the platform's text stack. Accessibility comes from the webview's accessibility tree, which screen readers already understand. Localization is ordinary frontend i18n, with strings out of the Rust business logic by construction (NFR-012).

**pdf.js closes the preview decision in one move.** One implementation on Windows, macOS, and Linux; no native PDF library to package alongside SILE's own dependencies; page-windowed rendering so a 2,000-page Bible does not rasterize on open. GUI-009's Open PDF and Open Output Folder stay, but as conveniences rather than as the fallback for a platform where preview could not be built — that contingency does not arise.

The viewer runs with JavaScript execution and external-link handling disabled. BibleCompose generated the PDF, so the risk is small; it is also nearly free to remove.

**It matches `easy-usfm`.** The same shell stack, the same platform-service pattern where Svelte components call typed interfaces and never Tauri directly, the same atomic-save and file-watching code to draw on. This is a real saving, and it is deliberately listed last: it would not be sufficient on its own, and the argument above stands without it.

## Consequences

**Binary size and memory are higher than a pure-Rust toolkit**, though far below Electron since the webview is the platform's. Acceptable for an application that also ships SILE, HarfBuzz, fontconfig, ICU, and libtexpdf.

**Webview versions vary across machines**, so the frontend targets a conservative baseline and CI runs GUI smoke tests on all three platforms. WebKitGTK on Linux is the usual source of surprises.

**pdf.js is a large dependency** and is pinned and vendored, not fetched.

**A code-organization rule follows.** No Svelte component imports Tauri APIs; every privileged call goes through a typed service interface, as in `easy-usfm`. Without that rule the frontend gradually becomes untestable and un-portable, and the discipline is only cheap if it starts at the first component.

**The door to embedding `easy-usfm`'s editor stays open.** Both frontends are Svelte over the same engine ([ADR-001](001-usfm-core.md)); a source-editing panel inside BibleCompose becomes a product decision rather than a rewrite. Not scoped, not promised — but it would have been foreclosed by option A.
